## First USB session

The adapter now cancels it with stall/clear before commit acknowledgement and queues frame submission on TinyUSB's task. This avoids the S3's no-op endpoint-close API and serializes submissions with commit.
- The restart fix uploaded through COM12 after manual BOOT/reset. Application hash verification succeeded. Esptool's watchdog reset booted the camera automatically; esptool then reported a serial-port error as COM12 disappeared. Windows confirmed the camera interface with driver status OK.

## Receive corruption and protected settings saves (0.2.1)

- The user reported a bright horizontal band and false occupancy. Live 0.2.0 samples alternated between roughly 34 and 186 degrees C with one receive error. Repeated palette saves reproduced vendor error `0x04` (data-available timeout). NVS writes interrupt this adapter's non-IRAM receive handler; see Espressif's [flash concurrency documentation](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/peripherals/spi_flash/spi_flash_concurrency.html). The previous error callback cleared the flag without restoring capture synchronization.
- Configuration writes now wait for the acquisition task to pause capture and disable its FIFO interrupt. A separate writer mutex avoids holding the configuration read mutex during that handshake. Timeouts cancel safely; saves do not proceed without acknowledgement. Capture restarts and discards two frames afterward. Native tests cover cancellation before/during acknowledgement and suppression of stale transitions on all three channels through a settling period.
- Receive errors discard the affected frame, mark detection unavailable, and reset capture/FIFO state with bounded retries. Calibration, allocated memory, Wi-Fi and USB enumeration are preserved. `SENSOR RECOVER` exercises a forced receive interruption and the same capture-reset path. The vendor's B0=3 reset and an attempted full sensor reinitialization did not restart capture reliably on this board; neither is used by the final implementation. Persistent hardware faults and initial startup failure can still require `REBOOT` or physical recovery.
- Final application SHA-256: `c0a8ad2d66549ca4cc35516a8a7a591f25fe81d05b9d7e588d96910b1deed8fd` (1,327,216-byte file). Upload hash verification passed; Windows again reported a serial-port disappearance after the watchdog reset, followed by successful COM13/HTTP reconnection. Saved White Hot palette, horizontal flip, cutoff 16, discovery enabled, Wi-Fi password presence and blank broker were preserved. Arduino adapter ZIP is now version 0.1.1; the proprietary archive remains byte-identical to its pinned hash.
- `scripts/check-sensor-recovery.ps1` passed 13 protected palette saves, restored the original configuration, then observed unavailable followed by learning on all channels after one forced capture interruption, without an ESP32 reboot or receive/allocation error. A second 13-save run passed during concurrent USB and HTTP capture. Final counters: 26 configuration pauses, one requested recovery, zero sensor errors and zero allocation failures. ## 1. Sensor, memory and recovery

Use the README's Arduino settings. Before replacing existing firmware, preserve any vendor firmware/configuration you need. Enter the ROM loader with BOOT/reset and verify that upload works. Repeat after intentionally booting the USB camera build. From 0.1.4 a separate diagnostic COM port is also available in normal operation; `BOOTLOADER` switches it to ROM upload mode.

With the thermal firmware, open setup Wi-Fi, view diagnostics and confirm frames increment with no viewers connected. `sensor_ready` should become true, learning should complete and free PSRAM should be nonzero. Compare a stable, high-emissivity target with an independent temperature reference over several temperatures; record error, warm-up drift and bad pixels. Confirm orientation and ROI alignment using a small warm target near all four corners. Do not infer calibrated correctness merely from plausible colours.

The adapter reads the factory calibration flash (0x17180 bytes) and invokes the supplied binary calibration functions. All-zero/all-FF calibration is rejected. The reference CRC hooks are no-ops; **calibration integrity is not cryptographically or CRC verified**. The HAL, FIFO timing, Kelvin scale and callback pixel layout still require live verification. Factory calibration flash writes are not implemented in the adapter.

The opaque library uses substantial static internal RAM with the stock linker, even though application image/background/YUY2 buffers use PSRAM. Inspect `free_internal_heap`, `min_internal_heap` and `largest_internal_block`, not just total heap. Verify every task starts, then repeat under maximum load. Establish at least 16 KB minimum internal heap headroom as an initial commissioning target and investigate any allocation failures/restarts before deployment. A custom PSRAM BSS SDK might improve headroom if measurements require it; it is not needed to compile USB.

Stop acquisition or disconnect the sensor only through a safe powered-off setup, then boot. Expect `unavailable`, no false clear/entry events and no stale HTTP snapshots. A restored valid stream must relearn. Receive faults attempt capture recovery from 0.2.1; persistent hardware faults or startup failure may still require a board restart. Confirm stored Wi-Fi/MQTT/ROI settings survive power cycling. To intentionally restore all ESP32 settings, use the IDE's erase-all-flash option for one upload and then disable it; this is separate from the sensor's factory calibration chip.

Verify the connector routes to S3 GPIO19/20; a serial bridge and power-only cable will not work. Restore `THERMAL_TEST_PATTERN=0` after this test.

## 3. Browser/configuration

Check initial setup AP and wrong-password recovery. Save real Wi-Fi credentials, verify DHCP/mDNS access and power-cycle persistence. Run `scripts/check-api.ps1`. Drag ROIs at each edge, save and reload; compare cyan overlay with native coordinates. Check temperature/FPS/health labels and background relearn. Submit out-of-bounds ROI, invalid JSON and a missing write header; expect rejection without changing saved configuration. Verify passwords are omitted from GET responses.

Open two streams and USB concurrently; a third WebSocket stream must be closed without stopping acquisition. Close/reopen tabs. Disconnect Wi-Fi and recover. Snapshots/streams must stop presenting new frames if the sensor fails; the status overlay must show the fault. Measure capture FPS and separately measure delivered browser/USB FPS. Use `scripts/check-video.ps1 -BaseUrl http://<device-ip>` for the WebSocket frame/header/pixel and host-arrival check, and `scripts/check-usb.ps1` for DirectShow. Check that USB contains no ROI, detection boxes or stripes, and that browser boxes align with the frame while mirrored and while dragging an unsaved ROI. Pause video and interrupt acquisition: snapshots should return 503 and browsers should cover stale images. Confirm reconnect and bounded memory under a slow client. Physically move a warm target while filming the target and display together to measure end-to-end delay; generated FPS alone is not latency.

## 4. Live detection

Learn an empty fixed scene. For each ROI and threshold, perform repeated entry, pause, slow movement and exit. Check the activation/clear delays against timestamps. Remain stationary for at least ten minutes: occupancy must persist. Introduce two overlapping occupants, remove one, then the other; only the last departure should clear. Test outside-ROI motion, tiny/noisy hot spots and a short crossing shorter than the activation delay. During relearning/invalid frames, state must become learning/unavailable without false clear events.

## 5. External MQTT broker

Subscribe at QoS 1 to the device prefix. Observe online availability, retained current state and non-retained edge events. Start a second subscription: it should immediately get availability/state but no old event. Confirm each real edge has a distinct event ID and any QoS duplicates repeat the same ID.

Stop the broker, generate several entries/exits, restart the broker: current state should republish, with no stale event replay. Repeat by removing Wi-Fi. Remove USB power and wait for broker last-will expiry: retained availability should become offline. Test invalid credentials and broker hostname, then correct them through the browser. Verify sensor failure changes `/state` to unavailable while device availability remains online. Close all video viewers and verify detection/MQTT still operate. Changing topic prefixes leaves previous retained messages in the broker; clear them deliberately with your broker tools if required.

## 6. Outdoor trials and 24-hour stability

Mount rigidly, let temperatures settle, learn an empty scene and document the full ROI/threshold configuration. At each distance test crossings, approaches, stationary presence and departures for the intended person/animal sizes. Include dawn, direct sun/shadow changes, dusk, wind, wet scenes and changing weather where practical. A warm surface and a living subject are both warm regions to this detector.
